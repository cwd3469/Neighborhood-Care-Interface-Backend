> 상태: **초안 (AI 작성, 본인 검토 필요)**
> `[직접 채울 것]` 표시는 기록에 근거가 없어 비워 둔 부분이다.
> 상세 근거: [Plan](../01-plan/features/security-fix.plan.md) · [Analysis](../03-analysis/security-fix.analysis.md) · [Report](../04-report/security-fix.report.md)

## 한 줄 요약

URL의 id만 바꾸면 보호자가 남의 어르신 건강기록을, 요양사가 담당이 아닌 어르신 데이터를 볼 수 있었다. 어르신 단위 접근 검사를 한 곳(`check_senior_access`)에 모으고, "요양사 담당"을 일정 기반으로 정의한 뒤, **권한 회귀 테스트 35개**로 고정했다.

> **IDOR**(Insecure Direct Object Reference): 서버가 "이 사람이 이 데이터를 볼 자격이 있는가"를 확인하지 않고, 요청에 들어온 id만 보고 데이터를 내주는 취약점. OWASP Top 10의 1위인 Broken Access Control에 속한다.

## 2. 문제

| 구분 | 내용 |
|------|------|
| 권한 상승 | `POST /register`가 body의 `role`을 그대로 저장 → 누구나 `"role":"admin"`으로 관리자 계정 생성 가능 |
| 보호자 IDOR | 어르신 상세, 방문 기록 상세, 기록별 활력징후, 어르신 활력징후 추이, AI 요약 4개 — 로그인만 하면 id로 남의 데이터 조회 |
| 목록 누출 (G-01) | `GET /records`에서 보호자가 관리자 분기로 흘러가 `senior_id` 없이 호출하면 전체 기록 반환 |
| 요양사 IDOR | 요양사는 검사 대상에서 아예 빠져 있어 담당이 아닌 어르신 데이터도 전부 조회 가능 |

## 3. 원인

1. **인증(로그인했는가)과 인가(이 데이터에 자격이 있는가)를 구분하지 않았다.** 대부분 엔드포인트가 `get_current_user`만 확인했다.
2. **검사가 엔드포인트마다 흩어질 구조였다.** 기준이 한 곳에 없으니 새 엔드포인트가 생기면 빠지기 쉬웠다.
3. **1차 계획 자체에 구멍이 있었다.** 계획서 FR-08이 "admin·caregiver는 검사 없이 기존과 동일"이었다. 보호자만 막고 요양사를 "내부 사용자"로 믿은 것이다.
4. **"요양사가 담당한다"는 관계가 데이터 모델에 없었다.** 보호자는 `guardian_senior_relations` 테이블이 있었지만, 요양사-어르신 관계는 정의된 적이 없었다.

### 요양사 "담당"을 어떻게 정의할지

| 안 | 내용 | 결정 |
|----|------|------|
| A | 검사 없음 | 탈락 — 문제 그대로 |
| **B** | 그 어르신 일정이 1건이라도 있으면 담당 | **채택** — 테이블 추가 없이 기존 데이터로 바로 동작 |
| C | 배정 테이블을 따로 둠 | 보류 — 담당 종료 관리가 필요해지면 전환. `access_service.py` 두 함수만 바꾸면 되도록 분리 |

### 목록은 403이 아니라 필터

단건 조회는 403을 주지만, 목록은 범위 밖 데이터를 쿼리에서 빼고 빈 배열을 준다. 목록에서 403을 주면 "남의 어르신 id가 존재한다"는 정보가 새고, 화면도 불필요하게 에러를 처리해야 하기 때문이다. `[확인 — 이 이유가 본인 의도와 같은지]`

## 6. 배운 점

- **"내부 사용자"도 믿지 않는다.** 요양사를 신뢰 대상으로 둔 1차 계획이 가장 큰 구멍이었다.
- **권한 기준은 한 곳에.** 헬퍼 하나와 `access_service.py` 하나로 모아 두니, 기준을 바꿀 때(B→C) 고칠 곳이 정해졌다.
- **목록과 상세의 기준이 다르면 그것도 버그다.** B1(목록)과 상세 검사가 어긋나 있던 것을 테스트를 쓰면서 발견했다.
- **보안 수정은 테스트로 고정해야 끝난다.** 수동 확인은 다음 수정 때 다시 깨져도 모른다.

## 7. 면접용 30초 버전

> 권한 점검을 하다 URL의 id만 바꾸면 다른 보호자의 어르신 건강기록이 보이는 IDOR 취약점을 발견했습니다. 원인은 로그인 여부만 보고 데이터 소유 관계를 확인하지 않은 것이었습니다. 어르신 단위 접근 검사를 헬퍼 하나로 모으고, 처음엔 보호자만 막았는데 점검해 보니 요양사도 담당이 아닌 어르신을 볼 수 있어서, 요양사 담당 관계를 일정 기반으로 정의해 같은 기준을 적용했습니다. 마지막으로 역할별 시나리오 35개를 회귀 테스트로 만들어 다시 깨지지 않게 고정했습니다.
