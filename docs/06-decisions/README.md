## 1. FHIR 이중 저장

**배경** — 방문 기록은 FHIR `QuestionnaireResponse`(설문 응답 표준 형식)로 받는다. 표준을 지키면 다른 의료 시스템과 주고받기 쉽지만, 응답 안의 혈압·맥박을 꺼내 "최근 30일 혈압 추이"를 그리려면 JSON을 매번 뒤져야 한다.

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. 원본 JSON만 저장 | 단순, 표준 그대로 | 추이·이상징후 조회마다 JSON 파싱 |
| B. 수치만 테이블로 정규화 | 쿼리 빠름 | 표준 원본을 잃음 |
| **C. 둘 다 (이중 저장)** | 원본 보존 + SQL로 추이 조회 | 저장 로직 복잡, 두 곳의 일관성 관리 |
| D. FHIR 전용 서버(HAPI 등) 도입 | 표준 완전 준수 | 이 규모엔 과함, 운영 부담 |

**결정: C.** `visit_records.fhir_response`에 원본을 저장하고, 같은 트랜잭션 안에서 `item.linkId`를 LOINC 코드(국제 검사 항목 코드, 예: 수축기 혈압 `8480-6`)로 매핑해 `vital_observations`에 한 행씩 저장한다. 각 행에는 FHIR `Observation` 형태의 JSON도 함께 둔다.

**대가**
- 원본과 구조화 행이 어긋날 수 있다 → 같은 트랜잭션(`flush` 후 일괄 `commit`)으로 묶어 둘 중 하나만 저장되는 일을 막았다.
- 컬럼 타입은 SQLAlchemy `JSON`이라 PostgreSQL에서 `json`으로 만들어진다(`jsonb` 아님). 원본 안을 조건으로 검색할 일이 생기면 `JSONB` + GIN 인덱스(JSON 내부 검색용 인덱스)로 바꿔야 한다.
- **현재 한계**: web의 기록 작성 화면은 메모만 보내고 `fhir_response`를 빈 객체로 채운다. 이중 저장 파이프라인은 백엔드에 구현돼 있지만 화면에서는 아직 활력징후가 들어오지 않는다. `[직접 채울 것 — 화면 연결 후 이 줄 수정]`

**바꿀 조건** — 외부 기관과 FHIR로 실제 연동하게 되면 D(전용 서버)를 검토한다.

## 2. Refresh Token: 별도 테이블 + SHA-256 해시

**배경** — Access Token(30분)만 쓰면 현장에서 기록을 입력하다 로그인이 끊긴다. 7일짜리 Refresh Token을 도입하면서, 탈취됐을 때 피해를 줄이는 방법이 필요했다.

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. JWT로만 발급 (DB 저장 없음) | 구현 단순 | 로그아웃해도 7일간 무효화 불가 |
| B. users 테이블에 컬럼 1개 | 단순 | 기기 1대만 지원 |
| **C. `refresh_tokens` 별도 테이블, 해시만 저장** | 다중 기기, 로그아웃 즉시 무효화, DB 유출 시 원문 노출 없음 | 테이블·조회 로직 추가 |

**결정: C**, 해시 함수는 **SHA-256**.
- 설계 단계에서는 bcrypt를 쓰려 했다. 그런데 토큰은 `secrets.token_urlsafe(64)`로 만든 **86자**이고, bcrypt는 72바이트까지만 처리한다. 현재 쓰는 bcrypt 5.0.0은 72바이트를 넘으면 `ValueError`를 낸다(실행해서 확인함).
- 비밀번호와 달리 refresh token은 사람이 고른 값이 아니라 충분히 긴 무작위 값이라, 일부러 느리게 만든 bcrypt가 필요 없다. 무차별 대입이 불가능한 길이이기 때문이다.

**대가 / 남은 개선점**
- 지금 `_find_matching_token`은 만료 안 된 토큰을 **전부 가져와 하나씩 비교**한다(bcrypt를 쓰려던 설계의 흔적). SHA-256은 같은 입력이면 항상 같은 값이 나오므로, `token_hash == sha256(원문)`으로 바로 조회하면 이미 있는 `token_hash` 인덱스를 쓸 수 있다. 토큰 수가 늘어나면 고칠 부분이다.
- 갱신할 때 refresh token을 새로 바꿔 주지 않는다(rotation 없음). 탈취된 토큰은 만료(7일)나 로그아웃 전까지 유효하다.

**바꿀 조건** — 사용자가 늘면 해시 직접 조회로 바꾸고, 보안 요구가 높아지면 rotation(갱신 때마다 새 토큰 발급 + 이전 토큰 폐기)을 넣는다.

## 3. AI 요약 DB 캐시

**배경** — 보호자가 방문 기록 카드를 열 때마다 Claude API를 부르면 비용이 쌓이고, 응답도 수 초씩 걸린다. 한 번 저장된 방문 기록의 내용은 거의 바뀌지 않는다.

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. 매번 생성 | 항상 최신 | 비용·지연이 열람 횟수에 비례 |
| B. 메모리 캐시(Redis 등) | 빠름 | 인프라 추가, 재시작 시 사라짐 |
| **C. DB 테이블에 저장** | 인프라 추가 없음, 영구 보관 | 기록이 수정되면 요약이 낡을 수 있음 |

**결정: C.**
- 기록 단위: `ai_summaries`(record_id 유일). 화면은 `GET /ai/summary`로 먼저 조회하고, 없을 때(404)만 `POST /ai/summarize`로 생성한다. 다시 생성하면 덮어쓴다.
- 어르신 단위 누적 요약: `senior_ai_summaries`(senior_id 유일, upsert). 최근 `limit`건(기본 10, 최대 30)만 쓰고 메모는 건당 200자로 자른다. 설계 추정 입력 토큰은 약 1,500~2,000개. `[확인 — 실제 호출 1회의 토큰 수·비용]`
- 권한 검사를 **LLM 호출 전에** 한다. 권한이 없는 요청은 비용 0원으로 끝난다(회귀 테스트로 확인).

**대가** — 방문 기록이 수정돼도 요약은 자동으로 갱신되지 않는다. 지금은 기록 수정 API가 없어서 문제가 되지 않는다.

**바꿀 조건** — 기록 수정 기능이 생기면, 수정 시 요약 삭제(무효화) 또는 `generated_at`과 기록 수정 시각을 비교하는 로직을 넣는다.

## 4. 요양사 담당 기준: 일정 기반(B안) + 기록 목록 B2

자세한 과정은 [회고 2](../05-retrospective/02-idor-access-control.md)와 [보안 보고서](../04-report/security-fix.report.md) 참고.

| 질문 | 결정 | 이유 |
|------|------|------|
| "담당"을 무엇으로 정의? | **B안: 그 어르신 일정이 1건 이상** | 테이블 추가 없이 기존 데이터로 바로 동작 |
| 요양사 기록 목록 범위? | **B2: 담당 어르신 기록 전체** (작성자 무관) | 상세 API와 기준이 같아짐, 교대 요양사가 이전 기록 확인 가능 |

**대가** — 일정이 끝난 뒤에도 계속 담당으로 남는다. 같은 어르신을 맡은 다른 요양사의 기록이 보인다.

**바꿀 조건** — 담당 종료 관리가 필요해지면 C안(배정 테이블)으로 전환한다. 판단 로직을 `services/access_service.py` 두 함수에 모아 두어서 호출부는 그대로 두고 그 파일만 바꾸면 된다.

## 5. 토큰은 httpOnly 쿠키 + Next.js 프록시

**배경** — 프론트가 토큰을 어디에 두느냐에 따라 XSS(악성 스크립트 삽입) 공격 시 피해가 달라진다.

| 선택지 | 장점 | 단점 |
|--------|------|------|
| A. localStorage + 브라우저에서 FastAPI 직접 호출 | 구현 단순 | XSS 한 번에 토큰 탈취 |
| **B. httpOnly 쿠키 + Next.js Route Handler가 대신 호출** | 브라우저 JS가 토큰을 읽을 수 없음 | 모든 API에 프록시 라우트 필요, 요청이 한 단계 더 거침 |

**결정: B.** 로그인 시 Route Handler가 FastAPI 응답의 토큰을 httpOnly 쿠키로 저장한다. 이후 Server Component와 Route Handler가 쿠키를 꺼내 `Authorization: Bearer` 헤더로 FastAPI를 부른다. `proxy.ts`는 토큰 만료를 미리 확인해 silent refresh(사용자 모르게 토큰 갱신)를 한다.

**대가**
- FastAPI 엔드포인트가 늘 때마다 `app/api/*` 프록시도 늘어난다.
- 화면에서 로그인 여부를 알려면 `/api/auth/me`를 거쳐야 한다(JS로 쿠키를 못 읽으니까).
- 역할별 리다이렉트는 화면 이동용일 뿐이고, 실제 권한 검사는 전부 FastAPI가 한다.

**바꿀 조건** — 모바일 앱 등 다른 클라이언트가 생기면, 웹 전용 프록시 대신 FastAPI 자체 쿠키 인증이나 API 게이트웨이를 검토한다.
